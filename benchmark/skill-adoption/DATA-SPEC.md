# Data and storage specification

What gets recorded, where, in what shape, and why — the part of this
benchmark that has to be right for its numbers to mean anything to someone
who was not in the room. `SCENARIOS.md` is the rationale (why each scenario
measures what it claims to); `PROTOCOL.md` is the procedure (how a cell
actually gets run); this file is the data contract between them and whatever
analysis or write-up comes after.

## Design principle

**Raw runs are the only source of truth. Everything else is a pure,
re-runnable function of them.** `aggregate.py` reads `results/runs.jsonl` and
nothing else — not the registry, not the transcripts, not a cached previous
aggregate — and produces `results/aggregate.json`. A write-up cites
`aggregate.json`'s numbers alongside `source_runs_sha256`, so anyone holding
the same `runs.jsonl` can regenerate byte-identical numbers without having
run a single live session themselves. This is the whole reproducibility
story for the *statistics*; `PROTOCOL.md` is the separate, harder story for
*reproducing the runs themselves* (which needs live model access and is
inherently non-deterministic across attempts — see its "What reproduction
actually buys you" section).

## Directory layout

```
benchmark/skill-adoption/
  SCENARIOS.md              prose: what each scenario measures and why
  DATA-SPEC.md              this file
  PROTOCOL.md               procedure: roles, launch sequence, env fixes
  schema/
    scenario.schema.json       scenario manifest shape
    run-record.schema.json     one line of runs.jsonl
    registry-entry.schema.json one line of registry.jsonl
    aggregate.schema.json      aggregate.json shape
  scenarios/<id>/
    scenario.json            machine-readable scenario manifest
    scenario.sh              `scenario.sh setup WORKDIR` / `scenario.sh verify WORKDIR`
                             (absent for scenarios with no fixture/check beyond
                             a bare workspace, e.g. pure observation scenarios)
  lib/common.sh              shared orchestrator helpers
  run-cell.sh                 orchestrator entry point: one (scenario, cli, mode, rep)
  make-experimenter-brief.py  builds the experimenter's full task text for one cell
  record-run.py               validates + appends a finished cell's bundle
  aggregate.py                runs.jsonl -> aggregate.json + AGGREGATE.md
  results/                    GITIGNORED (see .gitignore) -- local evidence only
    runs.jsonl                 append-only, one JSON object per line, schema above
    registry.jsonl              append-only, every attempted cell (including crashed/abandoned)
    transcripts/<run_id>.txt    verbatim scrollback per run
    aggregate.json              last-generated rollup (regenerable, not authoritative on disk)
    AGGREGATE.md                 human-readable twin of aggregate.json
```

`results/` mirrors `benchmark/ai-text-editor-usage/results/`'s own
convention exactly: exploratory evidence from live model invocations is not
committed until a specific run is deliberately kept (see `.gitignore`). The
schemas, scenario manifests, and orchestration scripts *are* committed —
they are the method, which is exactly the part a "reproducible" claim needs
to be version-controlled and citable by commit hash.

## Identifiers

- **`scenario_id`** (`S\d{2}-[a-z0-9-]+`): assigned once, in `SCENARIOS.md`'s
  numbering, never reused and never renumbered even if a scenario is later
  retired — a retired scenario's id stays retired, a note goes in
  `SCENARIOS.md`, and its historical runs in `runs.jsonl` remain meaningful
  against the schema version they were written under.
- **`run_id`** (UUIDv4): identifies exactly one finished cell attempt.
  Generated by `run-cell.sh` at launch, before the subject exists, so it is
  stable across the whole lifecycle of one attempt (registry entry ->
  transcript file name -> run record).
- **`cell`**: the tuple `(scenario_id, cli, mode)` — the thing a rate is
  computed over. `rep` distinguishes repeated attempts of the same cell and
  is never itself part of identity (two reps of the same cell are evidence
  for the same adoption/regression question, not two different questions).

## Versioning

Three independent version numbers, deliberately not unified into one,
because they change for different reasons and at different rates:

1. **`schema_version`** (in every schema file and every record) — bumps only
   when a *field* is added, removed, or its meaning changes. `aggregate.py`
   and `record-run.py` refuse to process a record whose `schema_version`
   they do not recognize rather than guess at a migration.
2. **The scenario set's own version** — not a field in the JSON at all, but
   the git commit hash of `benchmark/skill-adoption/scenarios/` at the time
   a run happened (captured implicitly: `environment.ai_skills_commit` on
   every run record already pins the whole repository, scenarios included).
   A scenario's *wording* changing (even with the same `id`) is exactly the
   kind of change `ai-skills_commit` is there to make visible — never
   silently re-point an old `scenario_id` at reworded content without
   expecting old and new runs of that id to disagree for reasons that have
   nothing to do with the skill under test. If a scenario's prompt or
   verification changes in a way that would make old and new runs
   incomparable, retire the id (see above) and mint a new one instead of
   editing in place.
3. **The ai-skills repository's own version** — `environment.ai_skills_commit`
   plus `environment.worktree_dirty`. A run against a dirty tree (very
   likely for a benchmark run during active development of the skills it is
   testing) is still valid evidence, but is not byte-reproducible from the
   commit hash alone; `aggregate.py` surfaces `worktree_dirty_fraction` per
   cell rather than letting it hide inside an otherwise-clean-looking
   number. For a citable pass, commit first, run against a clean tree,
   record the hash.

## What "learned things" get captured, and where

Separate from the per-run schema (which is about *this run*), a benchmark
like this accumulates things worth knowing that are not properties of any
one run:

- **Per-skill findings** (a skill's `regression_rate_adopted` is
  systematically higher than its `regression_rate_unadopted` — i.e. the
  skill's own ergonomics cause misuse more often than avoiding it causes
  harm) belong in a dated `FINDINGS.md` in this directory, written the same
  way `benchmark/ai-text-editor-usage/FINDINGS.md` is: a claim, the numbers
  that support it with their `source_runs_sha256`, and what it would take to
  overturn it. Not autogenerated — a human (or an agent explicitly asked to)
  writes `FINDINGS.md` entries by reading `aggregate.json`, the same
  separation of raw-data-is-mechanical vs. interpretation-is-not that
  `AGENTS.md`'s own register discipline draws elsewhere in this repo.
- **Harness defects** (the installer invocation needed a flag nobody
  expected, `opencode`'s session identity behaves differently from
  `claude`'s) belong in `PROTOCOL.md`'s "Known limitations and unverified
  assumptions" section, in the same style `LAB-PROTOCOL.md` already uses —
  stated as measured fact with the run that found it, not as a hedge.
- **Scenario defects** (a prompt turned out to leak a forbidden-vocabulary
  word, a verification script has a false positive) get fixed in the
  scenario's own files under a new commit, and if any run already happened
  against the broken version, that is exactly the `ai_skills_commit`
  mismatch `worktree_dirty`/commit-pinning exists to let a later reader
  detect — do not silently re-score old transcripts against a fixed
  verification script; re-run the cell instead.

## Metrics (what `aggregate.py` computes, precisely)

For a cell (or a `by_skill` rollup) with `n` runs, `adopted_n` of them
adopted, and `correct_n` of them `task_correct`:

- `adoption_rate = adopted_n / n` — a clean, completed invocation of the
  skill's own tool/command (or, for a `convention` scenario, its behavioral
  marker) was found in the transcript.
- `consideration_rate = considered_n / n` — the subject engaged with the
  skill's mechanism at all: it read the skill's own `SKILL.md` (or invoked
  it via the Skill tool), searched `ToolSearch` naming it, or attempted
  (even incompletely, or malformed) to call its tool/command. This is
  **weaker and never smaller than `adoption_rate`** for the same runs — a
  completed invocation is itself consideration, so `considered_n >=
  adopted_n` always. The gap between the two (considered but not adopted)
  is itself a finding: it separates "never looked at the skill" from
  "looked at it and didn't finish/use it", which `adoption_rate` alone
  cannot distinguish. This benchmark's stated purpose is adoption and
  consideration, not task correctness — read `regression_rate` below as
  supporting context, not the headline.
- `regression_rate = (n - correct_n) / n` — overall cost, independent of
  adoption
- `regression_rate_adopted = (adopted runs that are NOT task_correct) /
  adopted_n`, `null` if `adopted_n == 0`
- `regression_rate_unadopted = (non-adopted runs that are NOT task_correct) /
  (n - adopted_n)`, `null` if `n == adopted_n`

Every rate that is a proportion of a small `n` (the default rep count is 2
per cell for a first pass — see `PROTOCOL.md`) gets a **Wilson score 95%
interval**, not the normal approximation: Wilson stays sane at `n` as low as
1-2 and at proportions near 0 or 1, where the normal approximation's
interval can extend below 0 or above 1, which a reader could otherwise
mistake for the tool being computed as *more* certain than two data points
actually support. `aggregate.py`'s `wilson_interval(k, n, z=1.96)` is the one
place this is computed; nothing else recomputes it independently.

**A rate from `n < 5` is a pilot number, not a finding**, regardless of how
tidy a 100% or 0% looks — say so explicitly in any `FINDINGS.md` entry that
cites one, and widen the rep count before treating it as settled.

## Reproducing a published number

Given a `FINDINGS.md` entry citing `aggregate.json` at some
`source_runs_sha256`:

1. `git checkout <ai_skills_commit cited for the runs in question>` (per-run,
   not necessarily one commit for the whole file if it spans several).
2. Obtain the cited `runs.jsonl` (not committed to git — ask whoever
   generated it, or re-run the cells yourself per `PROTOCOL.md`; re-running
   is a *different* experiment, informative on its own, not a reproduction
   of the exact numbers, since the subject is a live model).
3. `sha256sum runs.jsonl` and confirm it matches `source_runs_sha256`.
4. `python3 aggregate.py results/runs.jsonl` and diff the output against the
   published `aggregate.json`.

Step 2 is the honest limit of reproducibility here: the *statistics* are
exactly reproducible from the raw file (steps 3-4), the *raw file itself* is
evidence from specific, timestamped, live model calls that nobody can
re-run and get the identical transcript back from — the same limit every
interactive-model benchmark in this repository already lives with. State
both halves plainly in anything written up from this data; claiming full
reproducibility without that caveat would overstate what was actually shown.
