## Why 1.4.0 used more tokens

The token-reduction goal was not met. The strongest explanation is increased
iteration count and workflow overhead, rather than a substantially larger
individual reasoning turn:

| Measure | 1.4.0 | 1.3.1 | Difference |
|---|---:|---:|---:|
| Telemetry usage records | 50 | 35 | +42.86% |
| Total usage tokens | 3,510,837 | 2,244,111 | +1,266,726 / +56.45% |
| Mean tokens per usage record | ~70,217 | ~64,117 | ~+9.5% |
| Tool-completion records | 48 | 36 | +33.33% |
| Wall-clock time | 121s | 419s | 1.4.0 was 298s faster |
| Plan shape | 7 work units / 2 goals | 7 work units / 2 goals | No outcome gain |

The telemetry counts are the best available local proxy; they are not a
billing estimate, and the event count is not guaranteed to equal the exact
number of model turns. The comparison is nevertheless sufficient to show that
1.4.0 performed about fifteen more usage cycles, while each cycle also averaged
about 9.5% more tokens.

Likely contributors, in descending importance:

1. The 1.4.0 workflow carried out more context-management work: snapshot
   initialization, audit-trigger checks, benchmark runs, and cache validation.
   Those tests demonstrated large helper-output reductions, but they measured
   shell output, not end-to-end model-visible tokens. A cache can therefore
   save bytes in a command result while increasing total tokens through its
   setup, metadata, and explanation.
2. The 1.4.0 plan introduced additional durable context artifacts such as the
   current context, snapshot index, manifest, and readiness marker. These are
   useful for staleness control, but the worker appears to have revisited more
   state during planning and review than the 1.3.1 run, which had no context
   snapshot in its artifact inventory.
3. The 1.4.0 run had review churn: a W07 re-review, a corrected exact-file
   inventory after an initially malformed inventory, and an explicit
   completion continuation. These are correctness improvements, but each
   re-read and continuation adds context cost.
4. The current skill’s richer contracts and safety boundaries increased the
   average cost of each cycle. The same plan shape and approved review show
   that this extra explanation did not produce a better measured result in
   this test.
5. The test used one long-lived worker context for the full planning/review
   cycle. That did not exercise the intended token-control strategy of a
   compact handoff after each goal. As context accumulated, later turns could
   repeatedly carry or restate earlier plan and review information.
6. The 1.3.1 helper correction (`awk -F'|'` in `update-step.sh`) avoided the
   field-parsing mismatch seen in 1.3.0. It likely reduced corrective retries,
   although the available telemetry cannot isolate exactly how many tokens it
   saved.

### Corrective changes for the next benchmark

- Make context loading lazy: load only the selected goal or step requested by
  the agent, and use the compact W/A index for discovery.
- Use hashes and version numbers as metadata first. Do not return file bodies
  unless the hash is stale, the file is requested, or a changed-file list is
  explicitly needed.
- Batch adversarial findings into one repair pass, then run one focused
  verification pass. Do not re-read the entire plan after every finding.
- Treat cache audits and benchmarks as one completion-boundary check rather
  than mandatory work during every goal/review cycle.
- At a goal boundary, emit a compact handoff containing changed paths,
  versions, hashes, open findings, and the next work unit. Then compact or use
  a fresh worker context where the host allows it. On the one-subchat VPS,
  prefer coordinator-triggered sequential handoffs rather than spawning more
  workers.
- Measure both command-output reduction and end-to-end telemetry tokens. The
  latter must be the acceptance metric for the token-reduction goal.

### Conclusion

1.4.0 was operationally faster but token-inefficient. The main failure was
allowing the cache and review safeguards to become additional conversation
work, while retaining a long-lived context and extra continuation cycles. The
next version should preserve hash/version safety while making unchanged state
nearly invisible to the model and limiting review to targeted changed files.
